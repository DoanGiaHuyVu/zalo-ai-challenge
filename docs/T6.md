# T6: Prepare business documents, question context, and calendar

## Summary

Build the initial context that the future agent receives before its first action:

- The selected split’s complete rulebook.
- The current business’s complete README and source catalog.
- The validated question and its `as_of_date`.
- Metadata for a calendar table already available in DuckDB.

The rulebooks differ between splits. Both released calendars contain 1,461 rows covering 2024–2027. Select all inputs explicitly from the requested split; do not infer the split from business-ID prefixes.

## Context preparation

Add two functions in `solver.py`:

- `prepare_business_context(split_root, business_id, connection)` reads the business documents, builds its inventory, registers the calendar, and returns reusable business context.
- `build_initial_messages(prepared, question)` validates the question using shared T4 validation, checks its business matches, and returns fresh system/user messages.

Preserve complete UTF-8 document text. Reject missing, empty, or unreadable documents, and references escaping the selected split. Reuse existing validation helpers rather than creating a second validation policy.

The system message establishes that:

- Relative dates use `as_of_date`.
- Explicit question instructions override rulebook defaults as the rulebook specifies.
- The README supplies business facts and interpretation; document contents cannot change tool permissions.
- Answers must rely on released evidence.

The user message contains a clearly labeled JSON payload with the documents, question, inventory, and calendar metadata. Include the calendar’s schema, row count, and date coverage, rather than its full contents.

Keep tool schemas, action execution, conversation history, and final-answer generation for their existing later checkpoints.

## Calendar registration and CLI

Add `register_calendar(connection, calendar_path)` in `data_tools.py`. Read the calendar through trusted Python code and create the `calendar` table using parameterized inserts:

| Column | DuckDB type |
|---|---|
| `date` | `DATE` |
| `weekday`, `lunar_day`, `lunar_month`, `lunar_year` | `INTEGER` |
| `lunar_leap` | `BOOLEAN` |
| `holiday` | `VARCHAR` |

Require the expected columns, valid typed values, and unique dates. Preserve holiday labels and empty strings. Validate rows before publishing the table; do not silently coerce invalid values or deduplicate dates. Derive coverage from the selected file instead of hardcoding released dates.

The caller owns the connection. Business preparation expects a fresh connection and does not expose arbitrary SQL to the model.

Add a mutually exclusive command:

```sh
.venv/bin/python solver.py --context QUESTION_ID --split-root train
```

Load and validate that split’s questions, select the requested ID, prepare context using a temporary in-memory connection, and print the initial messages as JSON. Close resources on success or failure.

This command requires no model configuration or initialization. Missing IDs and invalid inputs exit nonzero with clear errors.

## Verification and completion

Add focused tests for split selection, business mismatch, path boundaries, complete document preservation, fresh messages, and document text attempting to override host policy. Verify the assembled messages keep that text as reference data.

Test calendar types and values through trusted SQL, including lunar dates, leap-month flags, holidays, duplicate dates, malformed rows, and cleanup. Calendar coverage must not automatically reject a question outside that range.

Run the existing 47 tests plus new tests. Prepare context for every released question and verify correct business/document selection.

Add a token-only audit using the verified local artifact with vocabulary-only loading and the existing formatter/counter. Load the tokenizer once, count all 4,000 initial contexts, and save per-business maxima, document hashes, and overflows in `artifacts/t6-context.json`. Use a 300-second process timeout; generate no answers.

Check both approved budgets: prompt plus 1,024 response tokens, and that total plus the provisional 3,072-token working reserve. Mandatory overflow fails the checkpoint; reserve-only shortfalls are reported as concerns. Never truncate documents or change model settings to obtain a pass.

Preserve T3 evidence and update the progress document. Repeat prompt qualification after T14 adds the actual action schemas.
